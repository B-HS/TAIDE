      tunnel 등 외부 호스트를 목록에 등록한 뒤에만 그 호스트로의 접속이 통과하고(포트 무관), 등록하지

      호스트 기준 URL(`https://<host>/?t=...`)이 발급되는가, 목록이 비어 있으면 기존처럼

- [ ] (비밀번호 최소 길이) REMOTE 비밀번호를 8자 미만으로 설정하면 저장 버튼이 비활성화되거나 저장이
      거부되는가. 과거에 8자 미만 비밀번호를 이미 설정해 둔 세션은 재설정 전까지 그대로 로그인되는가
      (기존 짧은 비밀번호 강제 변경 없음)
- [ ] (잠금 카운터 분리) 로그인 폼에서 틀린 비밀번호를 반복 입력해 익명 접속이 잠긴 상태에서도, 이미
      발급받은 유효한 1회용 링크(nonce)로 접속하는 별도 기기는 잠기지 않고 정상 로그인되는가(익명
      실패 카운터와 nonce 보유 카운터가 분리되어 있는지)
- [ ] (stale nonce 별도 안내) 만료됐거나 이미 사용된 링크로 재접속을 시도하면 "비밀번호 오류"가 아니라
      "링크가 만료됨" 류의 별도 안내가 뜨는가, 이 시도를 여러 번 반복해도 잠금 카운터가 올라가지
      않는가(브루트포스 신호로 취급되지 않는지)
- [ ] (Hot Exit — 저장 왕복 타이핑 보존) ⌘S 로 저장한 직후(저장 완료 토스트가 뜨기 전후) 곧바로 몇
      글자를 더 입력한 뒤 강제종료 → 재시작하면, 저장 이후에 추가로 입력한 글자까지 유실 없이
      복원되는가(저장 완료 처리가 그 사이의 입력을 지우지 않는지)
- [ ] (Hot Exit — cross-file 미러) LSP Quick Fix/rename 등 코드 액션으로 **현재 열려 있지 않은 다른
      파일**이 편집된 직후 강제종료 → 재시작하면, 그 미열린 파일의 편집분도 hot-exit 복원 후보에
      포함되는가(탭을 실제로 열어 본 적 없어도 미러가 남아 있는지)
- [ ] (Hot Exit — 저장 직후 미러 부활 방지) 저장 직후 자동 미러 타이머가 도는 타이밍에 강제종료해도,
      재시작 시 방금 저장한 내용과 디스크가 동일한데 "디스크 변경됨" 오탐 배너가 뜨지 않는가
- [ ] (Hot Exit — 종료 플러시 지연 방지) git push 등 무거운 작업이 걸려 있는 상태에서 앱을 종료해도,
      그 작업이 끝날 때까지 무한정 대기하지 않고 일정 시간 내에 종료가 완료되는가(멈춰 보이지 않음)
- [ ] (회귀) 위 W6·"기능 확장 3차"의 remote 항목(터널 접속·잠금 60초 상한·1회용 링크·비밀번호 토글)과
      hot-exit 항목(탭 복원·디스크 변경 충돌 배너·untitled 복원)이 이번 하드닝 이후에도 동일하게
      동작하는가

## Wave C — Git 확장: 3-way 머지·hunk stage·커밋 상세·파일 히스토리·revert/tag·원격 checkout·blame 오버레이 (계약: docs/acknowledge/2026-08-15-wave-c-git-contract.md, 검토 정정: docs/acknowledge/2026-08-15-wave-c-review-fix-decisions.md)

> 검토 정정(review-fix-decisions)으로 계약 원문과 실제 구현이 갈린 지점 2곳(커밋 상세·파일 히스토리
> 배치)이 있다 — 아래 항목은 **실제 구현 기준**으로 적었다.

- [ ] (3-way 충돌 데코레이터) merge 충돌이 있는 파일을 열면 `<<<<<<<`/`=======`/`>>>>>>>` 블록마다
      Accept Current/Incoming/Both 액션이 뜨는가(git 패널 mergeChanges 그룹 클릭으로 진입 가능), 선택
      시 충돌 마커가 해당 내용으로 치환되고 자동으로 stage 되는가
- [ ] (hunk stage·unstage 위치) 워킹트리 변경 파일의 거터에서 hunk 단위 stage 가 되는가(기존 discard
      와 별개 액션), staged 목록에 반영되는가. **Unstage 는 staged 컨텍스트(파일을 staged diff 로
      열었을 때)에서만** 제공되고 워킹트리 에디터의 우클릭 메뉴에는 없는가(있으면 좌표 불일치 회귀 —
      L1-0 수정 확인)
- [ ] (line stage) 여러 줄만 선택해 부분 stage 하면 그 줄만 인덱스에 반영되는가. 서로 다른 두 hunk 에
      걸친 라인을 선택하면 부분 적용되지 않고 명시적 에러가 뜨는가(문서화된 제약 — L1-3)
- [ ] (미추적 파일 hunk stage) git 미추적(신규) 파일에서도 hunk/line stage 가 실패 없이 동작하는가
      (L1-1 수정 확인 — 과거엔 항상 실패했음)
- [ ] (커밋 상세) commit-graph 에서 커밋 행을 클릭하면 그 커밋의 변경 파일 목록이 패널 내부에
      **인라인**으로 펼쳐지는가(신규 diff 탭이 아님 — L0-2), 파일을 클릭하면 그 파일의 diff 가
      뜨는가. 병합 커밋·최초 커밋에서도 에러 없이 목록이 뜨는가
- [ ] (파일 히스토리) 탐색기/탭 우클릭 또는 팔레트에서 파일 히스토리를 열면 **모달(Dialog)**로 그
      파일의 커밋 목록이 뜨는가(사이드 패널이 아님 — L3-1), 커밋을 클릭하면 그 시점의 diff 가
      보이는가
- [ ] (revert) commit-graph 우클릭 → Revert 시 새 커밋이 생기는가. staged 변경이 있는 상태에서
      Revert 를 시도하면 거부되는가(L1-2 — 무관한 staged 변경이 함께 커밋되는 것을 막는 가드),
      충돌이 나면 자동으로 첫 충돌 파일이 열리는가(L0-1)
- [ ] (tag) commit-graph 우클릭으로 태그를 생성(annotated 기본, lightweight 옵션 선택 가능)·삭제할
      수 있는가
- [ ] (원격 브랜치 checkout) branch-switcher 에서 원격 전용 브랜치를 선택하면 로컬 추적 브랜치가
      생성되며 detached HEAD 가 아닌 정상 브랜치로 전환되는가, 동명 로컬 브랜치가 이미 있으면 에러
      없이 그 브랜치로 checkout 되는가
- [ ] (blame 오버레이) 팔레트 또는 탭 컨텍스트 메뉴에서 "Toggle Blame" 을 실행하면 파일 **전체**
      거터에 줄별 커밋·author blame 이 표시되는가(커서 줄 위 footer 표시와는 별개 기능 — "기능
      확장 2차" 의 blame footer 항목과 혼동 주의), 다시 실행하면 꺼지는가
- [ ] (팔레트 GIT 카테고리) 커맨드 팔레트에 GIT 카테고리가 신설되어 위 기능(충돌 해결 액션·revert·
      tag·원격 checkout·blame 토글·파일 히스토리 진입)들을 검색·실행할 수 있는가
- [ ] (회귀) 기존 diff 보기·hunk discard·git 패널 stage/unstage 전체 흐름·commit-graph 렌더링이 이번
      확장 후에도 정상 동작하는가

## Wave D — 탐색·검색: 팔레트 @/#/: 모드·Workspace Symbol·Breadcrumbs·Search Editor·gitignore (계약: docs/acknowledge/2026-08-15-wave-d-search-nav-contract.md, B3 결정: docs/acknowledge/2026-08-15-wave-d-b3-search-editor-decisions.md)

- [ ] (팔레트 @ 문서 심볼) 팔레트에서 `@` 를 입력하면 현재 활성 파일의 심볼 목록이 뜨는가, 선택하면

- [ ] (팔레트 : 줄 이동) 팔레트에서 `:123` 또는 `:123:45` 를 입력하면 활성 파일의 그 줄(과 열)로

- [ ] (monaco 내장 심볼 단축키 병존) `⇧⌘O`(문서 심볼)·`⌃G`(줄 이동)가 monaco 자체 오버레이로 그대로

- [ ] (Breadcrumbs) 에디터 pane 상단에 경로 세그먼트 + 커서 위치의 심볼 계층이 표시되는가, 커서를
      이동하면 심볼 부분이 갱신되는가, 세그먼트를 클릭하면 드롭다운(경로=폴더 형제 파일, 심볼=형제
      심볼)이 뜨고 선택 시 해당 파일/위치로 이동하는가
- [ ] (Search Editor 탭 생성) 검색 패널 또는 팔레트에서 Search Editor 를 열면 검색 쿼리·옵션·결과를
      담은 영속 탭이 생기는가, 결과에 전후 컨텍스트 줄이 함께 보이는가(기존 검색 패널의 단일 줄
      미리보기와 다름)
- [ ] (Search Editor 결과 열기) 결과 행을 클릭하면 실제 파일이 열리고 해당 줄로 이동하는가(가상

- [ ] (Search Editor 쿼리 고정 — 알려진 동작) Search Editor 탭에서 옵션(대소문자·정규식·gitignore·

- [ ] (gitignore 존중) 검색 패널/Search Editor 의 "gitignore 존중" 토글이 켜진 상태에서 `.gitignore`

- [ ] (excludeGlob) 검색 패널에 제외 glob 입력창이 있고, 패턴을 넣으면 매칭되는 파일이 결과에서

- [ ] (검색 히스토리) 검색을 실행하면 히스토리 드롭다운 맨 앞에 그 검색어가 추가되는가(중복 제거·
      상한 20), GitHub 동기화(W3)로 다운로드한 다른 기기에도 히스토리가 반영되는가
- [ ] (회귀) 기존 검색 패널의 텍스트/정규식/대소문자/단어 단위 검색과 팔레트의 파일/커맨드 모드가

      즉시 semantic 색이 사라지고 기존 syntax 색만 남는가(재등록 없이 반영, onDidChange 발화로
      즉시 재계산 — 2026-08-15 검토에서 "다음 편집까지 반영 안 됨" 회귀 수정), 다시 켜면 즉시
      다시 나타나는가
- [ ] (일반 구문 색 워시아웃 없음) 여러 번들 테마(예: github-dark·vitesse-dark·vscode-dark-plus)로
      바꿔가며 .ts/.rs 파일을 열어, semantic highlighting 이 꺼져 있어도 일반 구문 강조(변수·
      키워드·문자열·주석) 색이 테마 고유 색과 일치하는가(semantic rule append 가 실제 구문 색을
      바꾸던 회귀가 2026-08-15 검토에서 수정됨 — 특히 github-dark 의 변수 주황색, vitesse-dark 의

- [ ] (semantic delta) .rs 파일을 열어 둔 채 일부만 편집했을 때도 편집과 무관한 나머지 줄의

- [ ] (semantic Go) .go 파일에서 semantic 색이 표시되는가(gopls 는 매니페스트

      표시되지 않는다면 "조용한 0토큰"(계약 §3.1 마지막 항목) 재현 여부를 보고
- [ ] (format on type) 설정에서 "Format on Type" 켠 뒤 .rs 파일에서 `.`·`=`·`{` 등 트리거 문자

- [ ] (format on paste) 설정에서 "Format on Paste" 켠 뒤 들여쓰기가 흐트러진 코드를 .rs/.ts 파일에

- [ ] (스니펫 completion 즉시성) TAIDE 를 재시작한 뒤(설정 화면을 한 번도 열지 않은 새 세션)

## Wave G — AI: Inline Edit·AI 커밋 메시지 (계약: docs/acknowledge/2026-08-16-wave-g-ai-contract.md)

> Inline Edit 은 ViewZone/ContentWidget 레포 최초 도입 — 스크롤·워드랩·접기·다중 split pane 환경의
> 실제 렌더는 자동 테스트로 커버되지 않으므로 이 실기 확인이 유일한 검증이다. `features/ai.md`
> 가 상세 정본.

- [ ] (진입) 설정 AI 섹션에서 provider(Ollama Cloud 또는 Codex)+모델을 선택해 둔 상태에서, 에디터에서
      텍스트를 선택하고 `⌘I` 를 누르면 선택 영역 위에 입력창(ContentWidget)이 뜨는가. 선택 없이
      `⌘I` 를 누르면 현재 줄이 선택으로 승격되어 같은 위젯이 뜨는가
- [ ] (팔레트) 커맨드 팔레트에서 "AI: Edit Selection" 을 검색해 실행해도 같은 위젯이 뜨는가(⌘I 와
      동일 액션 트리거 확인)
- [ ] (제출→로딩→프리뷰) 입력창에 지시문을 쓰고 Return 을 누르면 스피너+"생성 중" 문구로 전환되고,
      응답이 오면 원본 선택 영역에 삭제(빨간 계열) 데코가 씌워지고 그 아래 제안 코드가 구문 강조된
      채로 나타나는가(ViewZone)
- [ ] (모델 무변경 — 핵심 불변식) 프리뷰가 떠 있는 동안 파일 내용 자체는 바뀌지 않았는가: 탭 제목에
      dirty 점(●)이 뜨지 않는가, 좌측 git gutter 표시가 그대로인가, 프리뷰 상태에서 앱을 종료했다가
      재시작해도(Hot Exit) 그 편집이 반영되지 않은 원본 그대로 복원되는가
- [ ] (수락·undo 1회) `⌘Enter` 또는 Accept 버튼으로 수락하면 실제로 텍스트가 교체되고 dirty 점이
      뜨는가. 그 직후 `⌘Z` 를 **한 번**만 눌렀을 때 수락 이전 원본으로 완전히 되돌아가는가(두 번
      이상 나눠 되돌아가지 않는가)
- [ ] (거절) 프리뷰 상태에서 `Esc` 또는 Reject 버튼을 누르면 데코·제안 코드가 사라지고 원본이 전혀
      바뀌지 않은 채 위젯이 닫히는가
- [ ] (생성 중 취소) 로딩 상태에서 `Esc` 또는 취소(×) 버튼을 누르면 요청이 취소되고 토스트가 뜨는가
- [ ] (빈 응답) 지시문이 모델이 코드를 반환하지 않을 만한 내용일 때(또는 provider 오류 시) 실패/빈
      응답 토스트가 뜨고 위젯이 정리되는가
- [ ] (편집 중 무효화) 생성 중이거나 프리뷰가 떠 있는 상태에서 같은 파일의 다른 곳을 타이핑하면
      위젯·데코·프리뷰가 즉시 사라지는가(stale 프리뷰가 남지 않는가)
- [ ] (세션 1개 제한) 위젯이 열려 있는 상태에서 `⌘I` 를 다시 누르면 새 위젯이 쌓이지 않고 기존
      입력창에 포커스만 이동하는가
- [ ] (탭 전환 정리) 위젯이 열린 채로 다른 탭으로 이동하면 위젯이 자동으로 정리되는가
- [ ] (코드펜스 스트립) 모델이 ```` ```lang ... ``` ```` 로 감싼 응답을 줘도 실제 삽입되는 코드에는
      펜스가 남지 않는가
- [ ] (커밋 메시지 생성) SCM 패널에서 파일을 stage 한 뒤 커밋 입력란 우측 상단 Sparkles 버튼을
      누르면 로딩 스피너로 바뀌고, 완료되면 diff 내용을 반영한 커밋 메시지가 입력란에 채워지는가
      (이미 텍스트가 있어도 덮어써지는가 — 확인 다이얼로그 없음, 의도된 동작)
- [ ] (staged·unstaged 둘 다 없음) 작업 트리에 변경이 전혀 없으면 Sparkles 버튼이 비활성이고, hover
      시 "요약할 변경 사항이 없음" 류 툴팁이 뜨는가(Wave H — `git.noChangesForCommitMessage`)
- [ ] (생성 중 취소) 커밋 메시지 생성 중 같은 버튼을 다시 누르면 취소되는가
- [ ] (절삭/제외 표기) 매우 큰 diff(예: 대용량 파일 다수 변경)를 stage 한 뒤 생성하면 성공 토스트에
      "diff가 잘렸습니다" 문구가 붙는가. `bun.lock`/`package-lock.json` 등 lock 파일을 stage 에
      포함해 생성하면 "N개 파일 제외" 문구가 붙는가(lock 파일 내용이 커밋 메시지에 언급되지
      않는가)
- [ ] (실패) provider 토큰이 없거나 잘못된 상태로 생성을 시도하면 실패 토스트가 뜨는가, 그
      description 에 원인(예: "AI provider is not configured")이 함께 표시되는가
- [ ] (긴 선택 영역) 60줄 이상의 함수를 선택해 편집을 요청했을 때 응답이 중간에 잘리지 않는가(잘리면
      절삭 에러 토스트로 실패해야 하며, 잘린 코드가 그대로 프리뷰/삽입되면 안 된다)
- [ ] (시크릿 파일 제외) `.env`/`id_rsa` 등을 stage 한 뒤 커밋 메시지를 생성해도 그 내용이 diff 로
      전송되지 않는가(skippedFiles 에 파일명만 나열)
- [ ] (자동완성 회귀) 설정 필드 리네임(`aiAutoTabProvider`→`aiProvider` 등) 이후에도 기존 auto-tab
      ghost text 제안이 그대로 동작하는가(W3 체크리스트 재확인)
- [ ] (프롬프트 오버라이드) `~/Library/Application Support/dev.taide.app.dev/prompts/inline-edit-default.json`
      또는 `commit-message-default.json` 을 직접 작성해 두면(스키마: `{version, system, user}`)
      재시작 후 그 프롬프트로 요청이 나가는가(네트워크 탭/프록시로 직접 확인은 어려우므로, 시스템
      프롬프트에 눈에 띄는 문구를 넣어 응답 스타일이 바뀌는지로 간접 확인해도 됨)
- [ ] (원격 세션) remote-control 로 연결한 세션에서도 ⌘I·커밋 메시지 생성이 동일하게 동작하는가

## Wave H — 키맵 엔진: chord·when (계약: docs/acknowledge/2026-08-16-wave-h-keymap-contract.md)

> chord·monaco 유예 창은 §3(멀티 리스너 팬아웃 레이스 수정)의 실효성이 자동 테스트로는 결정적으로
> 커버되지만, **실제 브라우저 타이밍**(진짜 물리 keydown 2회, 5000ms 타임아웃)에서의 최종 확증은
> 이 실기 확인이 유일하다. `features/keymap.md` 가 상세 정본.

- [ ] (⌘K ⌘S) 에디터 밖(예: 사이드바·상태바)에 포커스가 있는 상태에서 `⌘K` 를 누르면 상태바에
      "( ⌘K ) 다음 키 대기" 인디케이터가 뜨고, `⌘` 를 계속 쥔 채로 `S` 를 누르면(2단도 `⌘` 필요)
      키바인딩 에디터가 열리는가
- [ ] (⌘K ⌘S 무매칭) `⌘K` 로 대기 상태에 들어간 뒤 `⌘S` 가 아닌 다른 키(예: `X`, 또는 `⌘` 를 뗀
      맨 `S`)를 누르면 키바인딩 에디터는 열리지 않고 "일치하는 단축키가 없습니다" 인디케이터가
      잠깐 떴다가 사라지는가(그 입력이 다른 곳에 엉뚱하게 먹히지 않는가 — 오입력 무조건 흡수 확인)
- [ ] (터미널에서 ⌘K 보존) 터미널 패널에 포커스를 둔 상태에서 ⌘K 를 눌러도 앱 chord 대기에
      들어가지 않고(상태바에 대기 인디케이터가 뜨지 않는가), 터미널 자체의 ⌘K 동작(화면 지우기 등
      셸/터미널 설정에 따른 동작)이 그대로 발동하는가
- [ ] (⌘K ⌘S 타임아웃) `⌘K` 로 대기 상태에 들어간 뒤 아무 키도 안 누르고 5초 이상 기다리면 대기
      인디케이터가 자동으로 사라지는가
- [ ] (monaco chord 4건 보존 — 이 wave 의 핵심 회귀 상환) 에디터에 포커스를 두고 `⌘K` 를 누른 뒤
      **곧바로** `⌘B`/`⌘F`/`⌘=`/`⌘-` 를 각각 눌러보면(⌘K 마다 새로 시작) monaco 자신의 해당 chord
      동작이 정상 발동하는가, 그리고 그동안 앱 쪽 단일 키 바인딩(사이드바 토글·Find 위젯·폰트
      크기)이 **오발동하지 않는가**(예: ⌘K 이후 ⌘B 를 눌렀는데 사이드바가 토글되면 회귀)
- [ ] (⌘K ⌘C 주석 추가 — monaco 내장 chord 임의 표본) 에디터에서 몇 줄을 선택한 뒤 `⌘K` `⌘C` 를
      누르면(Add Line Comment) 선택 영역에 줄 주석이 붙는가, `⌘K` `⌘U` 로 제거되는가
- [ ] (팔레트 오픈 중 chord 안전) `⌘K` 로 chord 대기 상태에 들어간 직후 곧바로 `⌘⇧P` 로 팔레트를 열어
      재바인딩한 `taide.*` 커맨드를 실행해도, 팔레트의 독립 리스너가 2단 삼킴/유예 창 상태를 우회해
      오발동하지 않는가(critical→major 수정 확인 — `getKeymapChordDispatchSnapshot` 가드)
- [ ] (⌘⇧5 등 shift+기호 캡처) 키바인딩 에디터에서 임의 행을 재바인딩하며 `⌘⇧5`(미국 배열
      기준 `%`) 처럼 Shift+숫자/기호 조합을 캡처하면 정확히 그 조합으로 저장되고, 에디터에서 실제
      그 키 조합을 눌렀을 때 발동하는가(레이아웃과 무관하게 `event.code` 기반이므로 비-US 키보드
      에서도 물리적으로 같은 위치 키로 발동하는지 가능하면 함께 확인)
- [ ] (chord 캡처 UI) 키바인딩 에디터에서 아무 행이나 클릭 후 `⌘K` 를 누르면 "대기" 배지 + 프롬프트가
      뜨고, 이어서 `⌘⇧S` 등 아무 2단을 누르면 chord 로 저장되어 "⌘K ⌘⇧S" 형태로 표시되는가. 1단만
      원할 때는 확정 버튼(또는 Enter)으로 단일 키로 저장되는가
- [ ] (오버라이드 chord→단일 다운그레이드) chord 로 저장했던 행을 다시 캡처해 1단만으로 재확정하면
      chord 가 사라지고 단일 키 바인딩으로 표시가 바뀌는가(재바인딩 = 완전 재선언)
- [ ] (컨텍스트 인스펙터) 에디터 본문을 클릭해 포커스를 둔 **직후** 키바인딩 에디터를 열면
      (⌘K ⌘S 또는 팔레트) 인스펙터에 `editorTextFocus` 배지가 뜨는가 — 다이얼로그가 열려 있는 동안
      직접 에디터/터미널을 클릭해 배지를 바꿀 수는 **없다**(Radix 모달이 포커스를 다이얼로그 안에

- [ ] (taide.* 커스텀 액션 팔레트 활성화) 파일을 열어 에디터에 포커스를 둔 채 `⌘⇧P` → "Editor:

> 거부의 로직은 결정적으로 커버하지만, **실제 OS 창 생명주기·타이밍·시각 확인**은 이 실기가 유일한

### 창 열기 · 이동 · 닫기 · 복귀

- [ ] (새 창 열기) 아무 파일 탭이나 우클릭 → "Move into New Window" — 새 OS 창이 뜨고(제목표시줄에
      프로젝트 이름), 그 탭이 원래 창에서는 사라지고 새 창의 탭바에 나타나는가. 원래 창에 탭이
      남아 있다면 그대로 유지되는가
- [ ] (보조 창 크롬) 새로 뜬 창에 앱 사이드바·탐색 사이드바·상태바가 전혀 없고, 탭바 + 에디터
      영역만 있는가(`window-chrome.md` §5)
- [ ] (다른 프로젝트로 전환해도 보조 창 고정) main 창에서 다른 프로젝트를 활성화해도, 방금 연 보조
      창은 자기 프로젝트를 계속 그대로 보여주는가(전역 활성 프로젝트를 따라가지 않는가)
- [ ] (Move back to Main Window) 보조 창의 탭을 우클릭 → "Move back to Main Window" — 그 탭이
      main 창 탭바 끝에 나타나고 보조 창에서는 사라지는가. 그 탭이 보조 창의 마지막 탭이었다면
      보조 창이 자동으로 닫히는가
- [ ] (Move to Window N) 보조 창을 2개 이상 열어 둔 상태에서 한쪽 탭 우클릭 → "Move to Window 2"
      류 항목이 다른 열린 보조 창 수만큼 보이고, 선택하면 그 창으로 탭이 옮겨가는가
- [ ] (dirty·pinned 보존) 저장하지 않은 파일 탭(dirty 점 표시) 또는 pin 한 탭을 새 창으로
      이동하면, 이동 후에도 dirty 표시·pin 상태·미저장 내용이 그대로 남아 있는가(재로드 없이)
- [ ] (보조 창 닫기 = 앱 전체 종료 아님, **차단급 결함 상환 확인**) 보조 창을 OS 창 닫기 버튼
      (또는 ⌘W 로 마지막 탭까지 닫기)으로 닫아도 **main 창과 앱 전체는 그대로 살아 있는가** — 이
      항목이 §2 확정 사실 1 이 지적한 차단급 결함의 최종 확증이다
- [ ] (플레인 닫기 → main 복귀) 보조 창을 OS 창 닫기 버튼으로 닫으면(이동이 아니라) 그 창에 있던
      탭 전체가 main 창 탭바 끝에 나타나는가(0-손실 확인)
- [ ] (main 종료 시 전체 플러시) 보조 창 여러 개 + main 창에 각각 dirty 파일을 만들어 둔 상태에서
      main 창을 닫으면(⌘Q 도 함께 확인) 모든 창의 미저장 내용이 flush 된 뒤에야 앱이 실제로
      종료되는가(중간에 아무 창도 먼저 죽지 않는가)
- [ ] (재시작 복원) 보조 창을 열어 둔 채로 앱을 재시작하면 그 보조 창이 같은 프로젝트·같은 탭
      구성으로 다시 열리는가
- [ ] (보조 창 내 일반 레이아웃 조작, **차단급 결함 상환 확인**) 보조 창에 탭을 여러 개 연 상태에서
      그 창 안에서 탭 전환·개별 탭 닫기(창 자체는 유지)·pin 토글·split 이 정상 동작하는가(Phase E
      검토가 confirmed critical 로 잡은 결함 — 과거엔 보조 창의 close/activate/move-back/set-dirty
      등 레이아웃 커맨드 전부가 대상 탭을 찾지 못해 무동작이었다)

### 창 사이 공유 자원

- [ ] (같은 프로젝트를 두 창에서 편집 — LSP) 같은 프로젝트를 main 창과 보조 창 양쪽에 열어 둔 채,

- [ ] (같은 터미널 세션을 두 창에서 보기) 터미널 탭을 보조 창으로 옮긴 뒤 그 세션에 다시

- [ ] (capability 반생존 상환) 보조 창에서 파일을 외부 편집기로 고쳐(watcher 이벤트) 탐색기·git
      상태 등 이벤트 기반 갱신이 보조 창에도 정상 도착하는가(§2 확정 사실 4 확인)

### Zen 모드

- [ ] (진입/이탈) `⌘K Z` 를 누르면 사이드바·탭바·상태바(설정 기본값 기준)가 사라지고 3초짜리
      "Zen Mode · Press Esc to exit" 배너가 떴다 사라지는가. `Esc` 를 누르면 원상 복귀하는가
- [ ] (⌘K ⌘S 와의 공존) `⌘K` 를 누른 뒤 `⌘S`(키바인딩 에디터) 와 `Z`(Zen) 를 각각 눌러 둘 다
      정상 동작하는지 — 이 wave 가 수정한 "형제 chord" 회귀가 없는가
- [ ] (다이얼로그 위에서 Esc) Zen 모드에서 커맨드 팔레트나 다른 다이얼로그를 연 상태로 `Esc` 를
      누르면 다이얼로그만 닫히고 Zen 은 유지되는가(다이얼로그가 이미 닫혀 있을 때 `Esc` 를 누르면
      그제서야 Zen 이 꺼지는가)
- [ ] (사이드바 접힘 영속) Zen 이 아닌 상태에서 `⌘B` 로 사이드바를 접었다가 프로젝트를 전환했다
      되돌아오면 접힘 상태가 유지되는가
- [ ] (zen_fullscreen 설정) 설정 화면에서 "Fullscreen on Zen Mode" 를 켠 뒤 Zen 에 진입하면 OS
      창이 전체화면으로 전환되는가, Zen 을 나가면 전체화면도 해제되는가. 전체화면 상태에서 설정을
      끄면 즉시(Zen 을 나가지 않아도) 전체화면이 풀리는가
- [ ] (zen_hide_status_bar 설정) "Hide status bar in Zen Mode" 를 끈 상태로 Zen 에 진입하면
      사이드바·탭바는 사라지지만 상태바는 남아 있는가
- [ ] (보조 창은 Zen 영향 없음) 보조 창에서 `⌘K Z` 를 눌러도 아무 일도 일어나지 않는가(보조 창엔
      원래 사이드바·상태바가 없다)

- [ ] (SettingsChanged 실시간 반영 — 수동 편집 경로) settings.json 탭에서 값을 고쳐 저장하는 동안

- [ ] (SettingsChanged 실시간 반영 — sync 경로) Settings Sync 로 다운로드를 실행하면 결과가 설정

- [ ] (프롬프트 템플릿 편집) 설정 AI 섹션에서 프롬프트 3종(자동완성·인라인 편집·커밋 메시지) 편집
      진입점으로 각각 탭을 열고 수정·저장한 뒤, 실제 그 기능(자동완성/인라인 편집/AI 커밋 메시지)을

- [ ] (AppFile 은 hot-exit 미러 대상 아님 — 계약대로) settings.json 탭에 미저장 변경을 남긴 채 앱을

- [ ] (원격 세션의 AppFile 게이트 우회 차단, **RCE급 결함 상환 확인**) remote-control 로 접속한

## d-25 부팅 워처 attach 후절화 — Phase E 검토 반영 재검 (2026-08-20, 계약: docs/acknowledge/2026-08-20-boot-watcher-defer-contract.md)

> mock-app 하네스 부재로 `restore_project_watchers`(attach 순서·가드 범위·합성 방송·종료 중 취소)는
> 기계 테스트가 순수 선택 함수(`projects_pending_watcher_restore`) 하나만 고정하고, 나머지는 실기
> 확증이 유일한 검증 경로다(design-6). 아래 항목은 그 잔여를 겨냥한다 — 특히 1·2는 계약 §1 절대
> 조건("수렴 안 하는 소비자는 attach 완료 시 1회 refresh 로 보정")이 실제로 지켜지는지의 최종 확인.

- [ ] (git 공백 보정) 프로젝트 2개 이상을 열어 둔 채 앱 종료 → **비활성** 프로젝트의 워킹트리에서
      파일을 수정(또는 스테이징)해 git 상태를 바꿈 → 앱 재시작 → 그 프로젝트로 전환할 때까지
      **아무 것도 더 바꾸지 않은 채** 전환 → SCM 패널이 60초 대기(`staleTime`) 없이 전환 즉시
      최신 상태로 보이는가(합성 `git:status-changed` 1회가 정확히 이 케이스를 겨냥한다)
- [ ] (FILE.CONTENT 공백 보정) 어떤 프로젝트의 파일을 탭으로 열어 둔 채 앱 종료 → 그 파일을
      앱 밖(다른 에디터·터미널)에서 수정 → 앱 재시작 → 그 탭을 다시 클릭/포커스하지 **않아도**
      내용이 자동으로 새로 반영되는가(합성 `fs:changed` 1회 — 열린 파일 탭 경로 전체 대상).
      반영 후 "디스크 변경됨" 충돌 배너가 뜨지 않고 조용히 갱신되는 것이 정상(그 탭에서 미저장
      편집을 하지 않은 전제)
- [ ] (활성 프로젝트 우선 attach) 프로젝트 3개 이상 복원되도록 열어 둔 상태(그중 하나가 활성)로
      재시작 → 파일 탐색기·git 패널·탭 편집이 다른(비활성) 프로젝트보다 활성 프로젝트에서 먼저
      반응하는 체감이 있는가(순수 함수 테스트로 순서는 고정했으나, attach 자체의 체감 순서는
      실기 전용)
- [ ] (git 방송 중복 제거) 위 첫 항목 시나리오에서 git 패널의 새로고침 스피너/깜빡임이 프로젝트당
      1회만 일어나는가(과거엔 `git:status-changed`+`git:refs-changed` 2건이 동일 캐시를 중복
      무효화했다 — 이번엔 1건만 발신)
- [ ] (종료 중 취소) 프로젝트를 다수(3개 이상) 복원되도록 열어 둔 채 앱을 켜자마자(attach 가
      끝나기 전으로 추정되는 짧은 창 안에) ⌘Q 또는 창 닫기 → 남은 프로젝트의 attach 를 기다리지
      않고 정상적으로 종료되는가(hot-exit 플러시도 함께 정상 완료되는가)
- [ ] (재열기 중복 attach 없음) 부팅 직후(attach 가 아직 진행 중일 가능성이 있는 짧은 창) 방금
      복원 목록에 있던 프로젝트를 Welcome/최근 목록에서 즉시 다시 열기 → 정상 동작하고, 그
      프로젝트의 파일 변경 이벤트가 중복으로 오거나(같은 저장이 트리/탭에 두 번 반영) 워처가
      멈춰버리는 징후가 없는가

## d-35 Rust 하드닝 재검 (2026-08-25, 계약: docs/acknowledge/2026-08-25-d35-rust-hardening-contract.md)

> repo 경로 키 push/fetch 뮤텍스(`GitStore::push_fetch_lock`)는 동일 repo 요청끼리 직렬화 대기시키지만,
> `run_git` 서브프로세스 자체엔 타임아웃·kill 경로가 없다(적대적 검증 C3 — minor 로 처리, 코드
> 수정은 이월). 기계 검증으로 확인 불가능한 실사용 축이라 실기가 유일한 검증 경로다.

- [ ] (동일 repo 동시 push, 한쪽 망 단절) 같은 저장소를 데스크톱과 원격 세션(또는 두 원격 세션)
      양쪽에서 열어 둔 채, 한쪽에서 도달 불가능한 원격지로 push 를 시작해 네트워크 stall 상태로
      **의도적으로 멈추게** 함(예: 원격 URL 을 응답 없는 호스트로 임시 변경, 또는 VPN 을 끊어
      진행 중인 push 를 매달리게 함) → 그 상태에서 다른 쪽이 같은 repo 에 push/fetch 를 시도 →
      먼저 멈춘 push 가 끝나거나 취소되기 전까지 후행 요청이 **무기한 대기**하는가(스피너가
      영구히 도는가), 그리고 그 상태에서 다른 repo·다른 커맨드(파일 저장·git status 등)는
      영향받지 않고 정상 동작하는가(폭발 반경이 같은 repo 의 push/fetch 로 한정되는지)
- [ ] 위 상태에서 앱을 재시작하지 않고는 후행 요청이 회복되지 않는지(현재는 `run_git` 에 취소
      경로가 없어 앱 재시작만이 유일한 회복 수단 — 기대 동작대로인지 확인, 아니라면 후속 보고)
