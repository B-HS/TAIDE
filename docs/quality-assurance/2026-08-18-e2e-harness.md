# e2e 하네스 (경로 A — Playwright + remote-control) 가이드

> 정본: `docs/acknowledge/2026-08-18-pro-qa-design.md` §1·§2 (의존성 승인·하네스 설계 요지).
> 구현 위치: `e2e/`. 이 문서는 **실행법·준비 절차·격리 규약·시나리오 표·미확인 실측 항목·알려진 한계**를 다룬다.
> 하네스는 앱을 **절대 기동하지 않는다** — 사용자가 이미 켜 둔 `bun run tauri dev` 인스턴스의
> remote-control 서버(HTTP + WebSocket)에 접속만 한다.

---

## 1. 사용자 1회 준비 절차

매 로컬 환경에서 최초 1회(또는 REMOTE 비밀번호를 바꿀 때마다) 수행한다.

1. `TAIDE_E2E_NO_HMR=1 bun run tauri dev` 로 앱을 기동한다. (하네스가 대신 켜주지 않는다)
   - `TAIDE_E2E_NO_HMR=1` 은 dev 서버의 HMR WebSocket 을 끈다(`vite.config.ts` 의 `server.ws: false`).
     원격 페이지의 Vite 클라이언트가 1초 재접속 루프에 빠져 스위트 후반 webkit 프로세스를 열화시키던
     파일럿 결함 **C8 의 선결 조치**이며, 스펙이 14개를 넘은 지금은 **없이 돌리면 재발한다**(§7.1).
   - 대신 그 dev 세션에는 핫 리로드가 없다 — e2e 를 돌릴 때만 붙이고, 평소 개발은 그냥 `bun run tauri dev` 로 켠다.
     프로덕션 번들에는 HMR 클라이언트 자체가 없으므로 릴리스에는 아무 영향이 없다.
2. 앱의 설정 → REMOTE 섹션에서:
   - **비밀번호를 설정**한다 (8자 이상 — `REMOTE_PASSWORD_MIN_LEN`).
   - **"비밀번호만으로 접속 허용"(`remotePasswordOnlyLogin`)을 켠다.**
   - **원격 접속 활성화 토글을 켠다.**
3. 같은 비밀번호 값을 셸 환경변수로 export 한다.
   ```bash
   export TAIDE_E2E_PASSWORD='<REMOTE 비밀번호>'
   ```
   이 값은 **로그(콘솔·파일)·`storageState`·리포트 어디에도 기록되지 않는다** — `globalSetup` 이
   로그인 POST 요청 바디에만 담아 1회 전송한다.
4. `bun run e2e` 를 실행한다.

의존성은 이미 설치되어 있다(`@playwright/test@1.62.1` devDependency, `webkit` 바이너리만
`~/Library/Caches/ms-playwright/` 에 설치됨). 처음 클론한 환경이라면:

```bash
bun install
bunx playwright install webkit   # chromium·firefox 는 설치하지 않는다
```

## 2. 실행법

| 명령 | 동작 |
|------|------|
| `bun run e2e` | 스펙 25종 전체 실행 (workers 1·직렬·retries 0 — 12파일럿 + d-42 회귀 스펙 13 + 사용성 배치 3 스펙 14~16 + 사용성 배치 4 스펙 17~20 + 배치 4 웨이브 2 스펙 21~25) |
| `bun run e2e:ui` | 동일 + Playwright UI 모드(`--ui`) |
| `bun run typecheck:e2e` | `e2e/tsconfig.json` 기준 독립 타입체크 (루트 `bun run typecheck` 와 무관) |

스위트가 20종을 넘긴 뒤로 **`TAIDE_E2E_NO_HMR=1` 없이 켠 앱에 붙이면 후반 스펙이 무더기로 깨진다**(§1·§7.1).
하네스는 앱을 기동하지 않으므로 이 변수를 대신 넣어 줄 수단이 없다 — 실패가 9번째 전후부터
`window.__TAURI_INTERNALS__` 없음으로 시작되면 앱을 어떻게 켰는지부터 확인한다.

앱(`bun run tauri dev`)이 켜져 있지 않거나 REMOTE 준비가 안 되어 있으면 `globalSetup` 이
**즉시 fail-fast** 한다 — 포트 탐색 3단(로그 파싱 → `pgrep`+`lsof` 후보 → `/__taide/login` 프로브)이
전부 실패하면 사용자 준비 안내 문구와 함께 전체 런이 중단된다. `webServer` 블록은 의도적으로 없다.

## 3. 격리 규약

- **직렬 실행 고정** — `workers: 1`·`fullyParallel: false`·`retries: 0`. 여러 스펙이 같은 앱
  인스턴스를 공유하므로 병렬·재시도는 상태를 오염시킨다.
- **픽스처 프로젝트** — 각 스펙(정확히는 각 `test()`)마다 **리포 밖
  `~/Library/Caches/net.gumyo.taide.dev/e2e-fixtures/<runId>/`**(`E2E_FIXTURE_PROJECTS_DIR`, 구
  `dev.taide.app.dev` — 2026-08-29 개명) 에 새 git
  저장소를 만들고 `project_open` 으로 연다. 종료 시 `project_close` + 디렉토리 삭제. 사용자의
  실제 프로젝트 파일은 전혀 건드리지 않는다. (원래 `e2e/.tmp/` 였으나 Vite 워처가 픽스처의
  `tsconfig.json` 생성을 감지해 전 클라이언트 full-reload 를 강제해 리포 밖으로 이전 — C1,
  커밋 `3f56e46`. `os.tmpdir()` 은 macOS FSEvents 미감시로 기각. 정본 JSDoc: `e2e/lib/paths.ts`)
- **설정 스냅샷 원복** — `globalSetup` 이 런 시작 시 `settings_get` 전체를 스냅샷 저장하고,
  `globalTeardown` 이 런 종료 시 그 값 그대로 `settings_update` 로 되돌린다. 개별 스펙이 테마·
  `editorFontSize`·`shellOverride` 등을 바꿔도 런이 끝나면 항상 원래 값으로 복원된다.
- **git 커밋·push·revert 는 사용자 저장소에 만들지 않는다** — 단, 픽스처 루트 `<runId>/` 아래 매
  테스트가 새로 만드는 **1회용 픽스처 저장소**에서 `stage-unstage` 시나리오(스펙 7)가 전제하는
  baseline 커밋(`fixture-project.ts`)은 예외로 허용한다. 이 커밋에 한해 `-c commit.gpgsign=false`
  로 서명도 건너뛴다 — 사용자의 GPG 설정과 무관하게 매 런이 결정적으로 성공해야 하기 때문이다.
  두 예외 모두 **픽스처 저장소 안에서만** 유효하며, 사용자의 실제 프로젝트 저장소에는 절대
  적용되지 않는다.
- **조작은 UI, 검증만 IPC** — 모든 스펙은 앱 상태를 키보드·클릭으로만 바꾸고, `invoke` (`lib/ipc.ts`)
  는 결과 확인에만 쓴다. 유일한 예외는 다음 UI 입력을 구성하기 위한 **읽기**(예: `settings.json`
  본문을 새로 타이핑하기 전에 현재 `settings_get` 값을 읽어오는 것) — 이는 상태를 바꾸지 않으므로
  원칙 위반이 아니다.
- **언어 고정** — 매 테스트 시작 시 `settings.language` 를 `'en'` 으로 맞춘다(`lib/taide-fixture.ts`
  의 `page` 픽스처). 텍스트 매칭 셀렉터가 i18n 에 흔들리지 않도록 하기 위함이며, 런 종료 시 위
  설정 원복 규약으로 되돌아간다.
- **trace 산출물도 유출면이다** — `playwright.config.ts` 의 `outputDir` 는 `e2e/.tmp/test-results/`
  로 고정되어 있고(`e2e/.tmp/` 가 gitignore 대상), `.gitignore` 에도 `e2e/test-results/` 를 별도로
  추가해 이중 방어한다. `trace: 'retain-on-failure'` 로 실패 시 남는 `trace.zip` 에는 인증된 원격
  세션의 DOM 스냅샷·네트워크 로그·`taide_remote_session` 쿠키가 그대로 담기므로, 실수로 커밋되면
  세션 토큰과 사용자 파일 내용이 함께 유출된다.

### 3.1 활성 프로젝트 복원

`project_open` 은 백엔드의 `session.active_project` 를 새로 연 픽스처 프로젝트로 전환한다(원본:
`src-tauri/src/domain/project/service.rs`). 즉 **런 도중에는 데스크톱 메인 창에 보이는 "활성
프로젝트"가 일시적으로 픽스처 프로젝트로 바뀐다.** 파일 내용·git 이력 등 사용자 데이터는 전혀
건드리지 않는다.

`fixture-project.ts` 의 `createFixtureProject` 가 픽스처를 열기 **직전** `project_get_active` 로
그 시점의 활성 프로젝트 id 를 스냅샷하고, `closeFixtureProject` 가 픽스처를 닫은 뒤 그 값이 있으면
`project_activate` 로 되돌린다(없었으면 — 즉 런 시작 전 활성 프로젝트가 아예 없었으면 — 생략).
두 IPC 호출 모두 best-effort(`.catch`)로 감싸 있어, 복원 대상 프로젝트가 그사이 사라졌어도 테스트
정리 자체가 실패하지 않는다.

### 3.2 원격 게이트 4필드는 회귀 시 자동 복구가 불가능하다

스펙 11(`specs/11-remote-gate-fields-restore.e2e.ts`)은 원격 세션이 `shellOverride`/
`remotePasswordOnlyLogin`/`remoteAllowedHosts`/`aiOmlxBaseUrl` 를 `settings.json` 저장으로 바꾸려
해도 `strip_remote_gated_settings`(`dispatch.rs`)가 걸러 원값이 유지되는지 검증한다. 이 스펙이
**실패하는 유일한 시나리오(게이트 회귀)** 에서는 위 §3 "설정 스냅샷 원복" 규약이 이 4필드만큼은
구조적으로 지킬 수 없다 — `global-teardown.ts` 의 복원용 `settings_update` 호출도 원격 경로를
타므로 `strip_remote_gated_settings_patch`(`dispatch.rs`)가 복원 시도 자체를 포함해 이 4필드를
매번 `None` 으로 제거하기 때문이다. 즉 **회귀가 실제로 일어나면 하네스 스스로는 절대 되돌릴 수
없다.**

스펙 11 은 이를 감안해 4필드를 한 번에 시도하지 않고 **필드별로 시도 → 즉시 검증**하며, 하나라도
실제로 반영되면 남은 필드를 시도하지 않고 즉시 실패 메시지에 수동 복구 절차를 출력한다(대상
필드 · 설정 UI 경로 · `settings.json` 경로 · 원래 값). 이 스펙이 실패로 보고되면 **테스트 결과를
넘어 실제 보안 회귀로 취급**하고, 실패 메시지의 절차대로 수동 복구부터 한 뒤 원인을 조사한다.

## 4. 잠금 회피 규약

- 로그인 POST 는 **런당 정확히 1회**(`lib/login.ts`). 실패해도 재시도하지 않고 즉시 하드 중단한다.
- 실패 카운터는 **성공 전까지 리셋되지 않는다.** 연속으로 실패하는 런을 여러 번 돌리면 5회 임계
  이후 최대 60초 잠긴다.
- 429(잠금)/401(비밀번호 불일치)/그 외(미설정으로 판단)를 구분해서 처리한다 — 불일치일 때만
  즉시 실패로 보고하고, 잠금일 때는 대기 안내를, 미설정일 때는 준비 절차 안내를 출력한다.
- 잠금은 **익명 로그인 축**만 소모한다. 사용자 본인의 링크(nonce) 기반 접속에는 영향을 주지 않는다.
- **세션 만료 시 자동 재로그인은 최대 1회** — `lib/taide-fixture.ts` 의 `page` 픽스처가 첫 네비게이션
  결과 `/__taide/login` 에 착지하면 `loginOnce` 를 1회만 더 호출해 재시도하고, 그래도 로그인 페이지면
  즉시 중단한다(추가 재시도 없음). 런당 정확히 1회라는 위 원칙은 "정상 경로"에 대한 것이고, 이
  세션 만료 복구 1회는 별도의, 상한이 명시된 예외다 — 둘을 합쳐도 런 하나에서 로그인 POST 는 최대
  2회를 넘지 않는다.

## 6. 미확인 실측 항목 (파일럿 1회차에서 반드시 확인)

아래는 코드 정독만으로 확정할 수 없어 **실제 실행으로만 검증 가능한 가정**이다. 파일럿을 처음
돌릴 때 체크한다.

- [ ] **터미널 WebGL 예외 (최우선)** — `terminal-view.tsx` 의 `new WebglAddon()` 이 try/catch 없이
      호출된다. WebKit 헤드리스에 WebGL2 가 없으면 터미널 탭 마운트 자체가 실패할 수 있다.
      `specs/08-terminal-stream-osc133.e2e.ts` 는 `pageerror` 를 수집해 실패 시 진단 메시지로
      드러내지만, 실제로 실패하면 헤드리스 대신 headed 모드로 재시도하거나 터미널 관련 항목 전체를
      사람 실기로 반납해야 한다.
- [ ] **포트 발견 신뢰성** — 로그 로테이션(40KB·KeepOne)으로 포트 라인이 사라지는 빈도, `lsof` 후보
      가 remote 포트를 유일하게 특정하는지(agent hooks·IDE 서버와의 구분).
- [ ] **Playwright `APIRequestContext` 의 `Origin` 자동 부착 여부** — `lib/login.ts` 는 자동으로
      붙지 않는다고 가정하고 명시 헤더를 보낸다. 실측으로 확정한다(자동으로 붙어도 명시는 무해).
- [ ] **monaco 모듈 동일 인스턴스 재획득 가능성** — 이번 구현은 이 기법에 의존하지 않고 FS +
      `.monaco-editor` DOM + IPC 재조회만 사용한다. 성립 여부는 이번 하네스의 정확도와 무관하지만,
      추후 정밀도를 높이고 싶다면 파일럿에서 별도로 실측한다.
- [ ] **xterm 데코레이션 클래스명** — `specs/08` 의 OSC133 데코레이션 확인은
      `.xterm-decoration-overview-ruler`/`.xterm-decoration` 를 `expect.soft` 로만 확인한다(정식
      실패로 처리하지 않음). 실제 xterm 6.0.0 렌더 결과로 클래스명을 재확인해야 한다.
- [ ] **LSP 세션 준비 시간·심볼 제공 여부** — `specs/03`(문서 심볼)·`specs/05`(Workspace Symbol)
      은 `tsconfig.json`/`package.json` 없는 헐벗은 픽스처 폴더에서 vtsls(또는 대체 서버)가 실제로
      뜨는지에 의존한다. `LSP_SYMBOL_TIMEOUT_MS`(30초 — 파일럿 실측으로 15초에서 배증) 안에 옵션이 뜨지 않으면 이 두 스펙은 실패로
      보고되며, 그 경우 언어 서버 부트스트랩 조건을 다시 설계해야 한다.
- [ ] **`settings.language` 변경의 즉시 반영** — `applySettingsOverride` 로 언어를 바꾼 직후 이미
      마운트된 UI 텍스트가 재렌더되는지(TanStack Query 무효화 + 이벤트 구독을 통해 반영된다고
      가정). 반영이 늦으면 각 스펙 첫 어서션에서 낡은 언어의 텍스트가 잡혀 실패할 수 있다.
- [ ] **cmdk 팔레트의 `role="dialog"` 전제** — `lib/palette.ts` 는 shadcn `Dialog`(Radix) 래퍼가
      `role="dialog"` 를 노출한다고 가정하고 그 안에서 `input`/`option` 을 찾는다. cmdk 버전
      업그레이드 등으로 이 구조가 바뀌면 팔레트를 쓰는 6개 스펙(1·2·3·4·5·10·11)이 한꺼번에
      깨지므로, 실패 시 가장 먼저 확인할 지점이다.

## 7. 알려진 한계

- **원격 게이트 4필드 회귀는 자동 복구 불가** — §3.2 참고. 스펙 11 실패는 수동 복구가 필요한
  실제 보안 이벤트로 취급한다.
- **`buildFullRestorePatch` 는 `Option<T>` 필드를 `null` 로 되돌릴 수 없다**
  (`lib/settings.ts:15`) — `value ?? null` 은 `settings_get` 이 이미 내려준 JSON 값을 그대로
  다시 감싸는 것이라 입력이 `undefined` 인 경우가 없고, `SettingsPatch` 의 `Option<T>` 필드는
  백엔드에서 `null` 을 "값을 안 바꿈"으로 해석한다(`settings/service.rs`). 즉 어떤 스펙이
  `editorFontFamily`/`uiFontFamily`/`terminalFontFamily`/`keymapOverrides` 를 **처음 설정되지
  않은 상태(`null`)에서 값 있는 상태로** 바꾸면, `globalTeardown` 은 그 필드를 다시 `null` 로
  되돌리지 못한다. **현재 25스펙 중 이 네 필드를 건드리는 스펙은 없으므로 실질 영향은
  없다.** 이 조합을 건드리는 스펙을 추가할 때는 먼저 이 한계를 해소하거나(예: 필드별 언셋을
  지원하는 별도 IPC 경로 확인), 그 스펙만 별도 원복 전략을 마련해야 한다.

### 7.1 파일럿 C8(스위트 후반 열화) — dev HMR WebSocket 비활성으로 선결

`2026-08-25-d39-e2e-pilot-run.md` C8: 전체 스위트의 9번째 테스트 전후부터 나머지가 전부
`window.__TAURI_INTERNALS__ 없음`으로 연쇄 실패한다. 서버 무죄는 라이브 프로브로 확정됐고, 원인은
**원격 페이지의 Vite HMR 클라이언트**다.

- dev 에서 원격 페이지는 앱이 Vite dev 서버를 프록시해 내려준다(`domain/remote/serving.rs` `proxy_dev`).
  그래서 Vite 가 주입한 HMR 클라이언트가 **원격 오리진**에서 실행되고, 그 WebSocket 은 `vite-hmr` 을
  모르는 원격 서버를 향한다 → 핸드셰이크 실패 → 페이지 수명 내내 1초 재시도 루프. 페이지가 쌓이면
  하나의 webkit 프로세스가 열화된다(스위트마다 새 브라우저라 다음 실행이면 자가 회복).
- 선결 조치: `vite.config.ts` 에 **`TAIDE_E2E_NO_HMR=1` 일 때 `server.ws: false`**. Vite 8 의
  `server.ws` 는 "WebSocket 서버와 연결을 끈다"가 정의된 옵션이라, 클라이언트가 그 소켓을 열 일
  자체가 없어진다. 기본값은 그대로이므로 이 변수를 넣지 않은 개발 세션은 아무것도 달라지지 않고,
  프로덕션 번들에는 HMR 클라이언트가 아예 없어 릴리스와는 무관하다.
- 대가: 그 dev 세션 동안 **핫 리로드가 없다**(원격뿐 아니라 데스크톱 창도). e2e 를 돌릴 때만 켠다.
- [ ] **실측 대기** — 25스펙 전체를 `TAIDE_E2E_NO_HMR=1` 로 한 번 완주해 후반 연쇄 실패가 사라졌는지
      확인한다. 비교군이 필요하면 변수 없이 한 번 더 돌려 9번째 전후에서 깨지는지 본다.
      (하네스는 앱을 기동하지 않으므로 이 확인은 사용자만 할 수 있다.)
