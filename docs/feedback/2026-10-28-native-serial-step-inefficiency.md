# 전환 작업 방식이 너무 느림

## 무엇을 지적받았나

2026-10-28 사용자: "너 지금 한달 내내 이거 잡고있는건 알고있어?", "crate도 나눠놨는데 말이야 지금 작업방식이 너무 비효율적이야. 문서부터 바꿔 최대한 효율적으로, 정확하게, 완벽하게, 신속하게 처리할수있는방법으로".

## 왜 틀렸나

- 배치 안을 3~7 ID 단계로 잘게 나누고, 단계마다 구현을 직렬로 돌린 뒤 리뷰와 수정을 따로 왕복했습니다. 단계 하나에 1.5~7시간이 걸렸습니다.
- crate는 나뉘어 있지만 앱 crate의 통합 지점(`application.rs`·`host.rs`·`shell.rs`)이 하나라서 병렬로 돌릴 수 없었습니다. 이 구조 문제를 먼저 풀지 않고 직렬을 당연하게 여겼습니다.
- 작업자마다 원본 TS와 native 코드를 처음부터 다시 조사했습니다.
- 진척(%)과 남은 기간을 먼저 보고하지 않아, 사용자가 직접 물어야 알 수 있었습니다.

## 어떻게 고치나

`docs/memory/2026-10-28-native-lane-operations.md`의 lane 방식을 따릅니다. 통합 지점을 영역 파일로 나눈 뒤(wave 0), 영역 lane을 worktree·target 분리로 병렬 실행합니다. 사양은 영역마다 1회 쓰고, 리뷰는 lane 끝에 1회 합니다. 완료 기준은 낮추지 않습니다.

## 언제 적용하나

- 여러 영역에 걸친 장기 구현 작업에서, 단계가 직렬로 대기하는 시간이 길어질 때 적용합니다.
- 공유 파일 때문에 병렬이 막히면 그 파일을 먼저 나누는 구조 작업을 제안합니다.
- 장기 작업의 진행 보고에는 기능 기준 진척률과 남은 범위를 함께 적습니다.
