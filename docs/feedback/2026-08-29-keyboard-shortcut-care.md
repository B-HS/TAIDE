# 지적 — "이런 식으로 단축키 신경 잘 써야 해" (2026-08-29)

## 무엇을 지적받았나

- 같은 세션의 두 사건에 대한 총평: ① 내장 터미널에서 Claude Code 의 Shift+Enter 줄바꿈이
  동작하지 않았고(xterm.js 가 CR 로만 인코딩), ② Ctrl+G 가 사용자가 예상하지 못한 동작
  (Claude Code 의 외부 에디터 열기 → vim 실행)으로 이어져 혼란을 줬다.
- 요지: TAIDE 는 IDE 이므로 **키 입력이 앱·에디터·터미널·터미널 안의 TUI 중 어디로 가고
  어떻게 해석되는지**를 기능 설계 단계에서 항상 신경 써야 한다.

## 왜 틀렸나 (근본 원인)

- 터미널 pane 은 키 입력의 최종 소비자가 셸이 아니라 **그 위에서 도는 TUI(Claude Code·vim
  등)일 수 있다**는 전제를 기능 구현 시 검토 항목으로 두지 않았다. 터미널 에뮬레이터가
  구분 못 하는 키 조합(Shift+Enter 등)은 TUI 가 아무리 지원해도 도달하지 않는다.
- 임베드 터미널의 키 경로는 3층(앱 keymap → xterm 커스텀 핸들러 → PTY/TUI)인데, 각 층이
  어떤 키를 삼키고 어떤 키를 통과시키는지의 **정책 표가 없다.**

## 어떻게 고치나

- 키 입력 관련 기능(단축키 추가·터미널·에디터 포커스 처리)을 만지면 반드시 확인:
  1. 앱 keymap(`shared/lib/keymap/keymap.ts`)과 충돌하는가 — 터미널/에디터 포커스 시 누가
     이기는가.
  2. 터미널 포커스에서는 **기본적으로 키를 PTY 로 통과**시키는 것이 원칙(VS Code 의
     commandsToSkipShell 모델). 앱이 가로채는 키는 명시적 화이트리스트여야 한다.
  3. xterm.js 가 인코딩 못 하는 조합(kitty protocol 계열)은 TUI 도달 여부를 실기로 확인하고,
     필요 시 커스텀 키 핸들러로 변환한다(Shift+Enter → LF 선례:
     `acknowledge/2026-08-29-terminal-shift-enter-decision.md`).
  4. 대상 TUI(특히 Claude Code)의 기본 키바인딩 표를 근거로 판단한다 — Claude Code 는
     Ctrl+G(외부 에디터)·Ctrl+B(백그라운드)·Ctrl+T(할 일)·Ctrl+O(트랜스크립트)·Ctrl+R(히스토리
     검색)·Ctrl+J(줄바꿈)·Ctrl+S(초안 저장) 등을 소비한다(공식 keybindings 문서 기준).

## 언제 적용하나

- 단축키·키맵·터미널 키 처리·에디터 포커스 관련 기능을 추가·수정하는 모든 작업에서.
- 새 pane 종류(터미널·에디터 외)를 추가해 포커스 라우팅이 늘어날 때.
