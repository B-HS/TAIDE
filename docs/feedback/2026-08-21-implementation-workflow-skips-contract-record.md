# 단독 구현 워크플로가 계약 §3 구현 기록을 누락 (2026-08-21)

## 무엇을 지적받았나

T2-B(settings-view 섹션 위젯 분해)를 단독 sonnet+xhigh 구현 워크플로(wf_8b86dab0-684)에
위임했더니, 계약 문서(`docs/acknowledge/2026-08-21-t2b-settings-view-contract.md`)의
"구현 완료 기록" 섹션을 채우지 않은 채 완료 보고만 돌아왔다. 메인 세션이 워크플로의 완료
보고(레포 밖 세션 스크래치패드 `d29-impl-report.json`)를 읽고 계약 §3 전체를 사후에
전사해야 했다. Phase E 4렌즈 검토(contract-6)가 이 사실 자체와, 그 근거가 세션 종료 후
검증 불가능한 스크래치패드 파일 하나뿐이라는 점을 지적했다. 같은 유형(세션 산출물을 계약의
유일한 근거로 지목)이 하루 전 `docs/acknowledge/2026-08-20-t2a-dedup-contract.md` §4.3
("상세는 이 세션의 구현 보고를 따른다")에서도 있었다 — 반복되는 패턴인데도 이때까지
`docs/feedback` 에 승격되지 않았다.

## 왜 틀렸나

계약 문서는 "이후 세션에서도 동일한 이해를 유지"하기 위한 것이다(ai-process.md §1.1·§5).
구현 워크플로가 계약 §3(무엇을 어떻게 나눴는지, 배선 결정과 근거, 검증 결과)을 직접 채우지
않으면, 그 정보의 유일한 출처가 워크플로 완료 보고 텍스트 — 레포 밖 세션 스크래치패드
경로 — 로 남는다. 스크래치패드는 세션이 끝나면 사라지므로, 다음 세션(또는 이번처럼 Phase E
검토 세션)이 "왜 이렇게 나눴는가"를 되짚을 방법이 없어진다. 메인 세션이 사후 전사로 이를
메웠지만, 전사 과정에서 §3.1 줄수 오기(91 vs 실제 92)·§3.2 서술 오류("8개 섹션" vs 실제
7개+예외 1) 같은 부정확이 실제로 섞여 들어갔다(contract-3) — 사후 전사 자체가 손실이 있는
경로임을 이 세션이 증명한 셈이다.

## 어떻게 고치나

- 단독 구현 워크플로에 위임할 때는 **완료 조건에 "계약 §3(또는 해당 계약 문서의 구현 기록
  섹션)을 직접 채운 뒤에만 완료로 보고할 것"을 명시**한다. 워크플로 프롬프트/태스크 지시문에
  이 요구를 넣는다.
- 워크플로가 §3 를 누락한 채 완료 보고를 하면, 메인 세션은 그 보고를 곧바로 계약에
  전사하지 말고 **워크플로에 재작업(§3 직접 작성)을 요청**하는 것을 우선한다. 부득이 메인이
  대신 전사해야 하면(이번처럼), 전사 후 실코드(`wc -l`·`grep`)로 수치·나열을 반드시
  재대조한다 — 사후 전사는 손실 가능성이 있다는 전제 하에 검증 단계를 하나 추가한다.
- 계약 문서 안에서 세션 산출물을 근거로 지목해야 하는 경우, **레포 밖 스크래치패드 경로 대신
  검증 가능한 근거**(커밋 해시, 재실행 가능한 명령, 실코드 grep 결과)를 인용한다.

## 언제 적용하나

이 프로젝트(TAIDE)에서 구현을 단독 워크플로(sonnet+xhigh 등)에 위임하고 그 결과를
`docs/acknowledge` 계약 문서에 기록해야 하는 모든 경우. 특히 여러 파일에 걸친 분해·리팩토링
계약처럼 §3 급의 상세 기록이 필요한 작업에서 적용한다. 오타 수정처럼 체크리스트 자체가
생략되는 단순 작업에는 해당하지 않는다.
