# 지적 — "승인 창이 수십 번 뜬다, 5시간 넘게 모니터링해야 한다" (2026-09-04~05)

## 무엇을 지적받았나

배치 3·4 workflow(총 8회, 에이전트 60여 개)가 도는 동안 셸 명령 승인 프롬프트가 분당 수십 건 떠서
사용자가 세션 내내 화면을 지켜야 했다. 세 차례 강한 불만 표명.

## 왜 틀렸나 (근본 원인)

- 허용 목록(`.claude/settings.json` `permissions.allow`)은 명령 prefix 매칭이라 에이전트가 쓰는
  `for/while` 루프·`$(…)` 치환·heredoc(`python3 -`·`cat >`)·따옴표 붙은 `export PATH="…"`·여러 줄
  grep 패턴을 못 잡는다. 초기 workflow 프롬프트에 셸 사용 제한이 없어 에이전트가 파일 편집까지
  셸로 했다.
- 전체 허용(`Bash(*)`)을 에이전트가 스스로 넣는 것은 auto 모드 분류기가 차단한다 — 사용자만
  `/permissions` 또는 `!` 명령으로 추가할 수 있는데, 이 사실을 세션 초반에 알리지 않았다.

## 어떻게 고치나

- 모든 workflow 공통 규칙에 명시: 파일 수정은 Edit/Write 도구로만, 셸은 `grep`·`sed -n`·`cat`·
  `git diff`·검증 명령(`bun run …`·`bun test`·`cargo …`)을 **한 줄 단순 명령**으로만, 루프·치환·
  heredoc·python3 금지. (배치 4 계약 §0 에 반영, 웨이브 2 부터 적용)
- 읽기·검증 명령 prefix 는 `.claude/settings.json` 에 유지(`d7424f7`·`8aa712a` 커밋분).
- 장시간 workflow 가 예상되는 세션은 시작 시 사용자에게 `Bash(*)` 추가 여부를 1줄로 묻는다.
- 진행 상황 질문에는 단계별 예상 시간 표로 답하고, "배치·웨이브" 같은 내부 용어가 새 작업으로
  오해되지 않게 "같은 요청의 단계" 임을 밝힌다.

## 언제 적용하나

- Workflow 를 2회 이상 연속 기동하거나 1시간 이상 걸릴 것으로 예상되는 모든 세션.
- 사용자가 자리를 비우거나 모니터링 부담을 언급한 경우.
