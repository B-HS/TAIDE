# 편집 표면 버그 전수 조사 2차 — LSP·전환 중 저장·보조 창·터미널·세션/슬롯·탭 메뉴·트리/워처/검색 (2026-09-17)

> 범위: 1차 조사(`2026-09-17-editing-surface-bug-audit.md`)가 §5 에 "못 본 범위"로 남긴 축을 이어받는 읽기 전용 조사. LSP 문서 동기·세션 수명, 저장 중 전환(프로젝트 닫기·슬롯 닫기·창 닫기·종료), 보조 창 수명, 터미널 세션, 세션/셸 슬롯/id, 탭 컨텍스트 메뉴·닫기 계열, 트리·워처·검색.
> 실행: 7관점 finder 병렬(읽기 전용, 시간 상한) → 후보 건별 반박 검증(독립 검증자, 소스 재추적) → 메인 분류.
> 반박 규칙(1차와 동일): 검증자는 세 가지 중 하나라도 성립하면 기각(refuted)한다. (a) 워킹트리·최근 커밋에서 이미 수정됨, (b) `docs/acknowledge`·`docs/HANDOFF.md`·`docs/backlog.md`·**1차 조사 §1/§3/§4** 에서 이미 검토 후 기각·보류로 확정됨, (c) 소스 추적상 재현이 성립하지 않음. 셋 다 아니면 생존.
> severity 열은 finder 원등급이 아니라 **검증자 조정값**이다. finder 등급과 갈린 경우 `minor→major` 처럼 둘 다 적었다.
> **조사 시점 주의**: 이 조사는 d-65·d-66 이 워킹트리를 수정하는 중에 돌았다. 아래 findings 의 줄 번호는 조사 시점 워킹트리 기준이며, d-66 이 동시 수정 중인 파일(`src/widgets/editor-pane/**`, `src/entities/layout/tab-path-change.ts`, `src-tauri/src/domain/layout/service.rs`, `src-tauri/src/domain/project/{service.rs,shell_slots.rs}`, `src/widgets/explorer/**`)에 걸린 항목은 각 상세의 주의점에 재확인 필요를 명시했다.

## 2. 생존 발견 상세

### 1. [lsp-sync-1] `src/widgets/editor-pane/use-lsp-session.ts:140` — split view 에서 `didChange` 가 두 번 나간다

- **증상**: 같은 파일을 두 pane 의 활성 탭으로 띄운 뒤 한 글자만 입력해도 언어 서버의 문서 사본에는 두 글자가 들어간다. 이후 그 파일의 진단(없는 오류/놓친 오류)·완성·호버·정의 이동이 전부 오염된 사본 기준으로 계산된다.
- **재현**: ① TS 파일을 연다(vtsls 세션 Running). ② pane 을 분할하고 같은 파일을 오른쪽 pane 에도 활성 탭으로 둔다. ③ 아무 곳에나 `x` 한 글자를 입력한다 → 서버 사본은 `xx`. ④ 몇 글자 더 치면 화면 버퍼와 완전히 어긋나 존재하지 않는 구문 오류 물결선이 뜬다. ⑤ 한쪽 pane 의 탭을 닫아도 `openDocuments` refcount 가 1로 남아 `didClose` 가 안 나가므로 **모든 pane 에서 닫았다 다시 열기 전까지 복구되지 않는다.**
- **원인**: `attachLspSession` 이 `EditorPane` 마다 한 번씩 돌며 모델에 자기 리스너를 건다.

  중복 방지는 문서 개방에만 있다 — `acquireDocument`(`lsp-session-registry.ts:665-670`)는 `openDocuments` 가 uri 별 refcount 라 `current === 0` 일 때만 `didOpen` 을 보내고, `ensureLanguageRegistered`(:644)도 `languageDisposables.has` 로 막는다. 그런데 위 `onDidChangeContent` 등록만 그 refcount 밖에 있다. `grep -rn "onDidChangeContent" src/` 전수 결과 `didChange` 를 쏘는 등록처는 이 한 곳뿐이고 가드가 없다. 그리고 `client.didChange`(`src/shared/lib/lsp/client.ts:208-214`)는 `currentVersion + 1` 만 보고 무조건 notify 하므로, 한 번의 키 입력이 동일한 incremental change 를 version N+1, N+2 로 두 번 전송한다.
- **수정안**: 변경 리스너를 문서 단위로 refcount 한다 — 이미 uri 별 refcount 를 들고 있는 `acquireDocument`/`releaseDocument`(`lsp-session-registry.ts:665-696`)가 정확한 자리다. `ConnectionState` 에 `contentSubscriptions: Map<string, { disposable: Disposable; refs: number }>` 를 두고, `acquireDocument` 의 `current === 0` 분기에서만 `monaco.editor.getModel(monaco.Uri.parse(uri))` 로 모델을 얻어 등록, `releaseDocument` 의 `current <= 1` 분기에서 `didClose` 와 함께 dispose 한다. 그러면 `attachLspSession` 은 `contentChangeDisposable` 을 자체 보유하지 않고 `releaseDocument` 호출만 남는다(cleanup 로직 :152-165 도 단순해진다). 회귀 테스트: 같은 `(record, uri)` 로 `acquireDocument` 를 2번 부른 뒤 모델에 1회 편집을 가해 `client.didChange` 가 정확히 1번인지, `releaseDocument` 1회 후에도 1번, 2회 후에는 0번인지 단언.
- **주의점(fixNote)**: `reinitializeSession`(:764-810)의 `didOpen` 재전송 루프와 정합되는지 확인할 것 — 이미 열려 있던 uri 는 `current > 0` 이라 새 구독이 재등록되지 않는 것이 맞다. `src/widgets/editor-pane/**` 는 d-66 동시 수정 경로다(조사 시점 워킹트리에서 `use-lsp-session.ts` 자체는 미변경이었다).

- **수정안**: `read_children` 에서 **심링크 엔트리에 한해서만** 추가 `std::fs::metadata`(추적) 한 번을 지불해 종류를 정한다 — `is_indexable_file` 과 대칭이고, 비-심링크 엔트리의 `d_type` 최적화는 그대로 보존된다. 끊어진 심링크는 `metadata` 실패 → 지금처럼 `File` 행으로 남긴다. `has_children` 도 재판정된 kind 기준으로 `directory_has_children` 을 호출해야 펼침 화살표가 생긴다. `ensure_existing_file` 은 그대로 둬도 된다 — 트리가 kind 를 올바르게 주면 프런트가 자연히 펼치기로 라우팅해 애초에 `layout_open_tab` 을 호출하지 않는다.
- **주의점(fixNote)**: 기존 테스트 `심링크는_대상과_무관하게_파일로_표시된다`(:445-461)·`심링크는_자식이_없는_것으로_취급되고…`(:470-480)는 **의도된 사용자 동작을 고정한 것이 아니라 리팩토링 불변성을 고정한 것**이다(JSDoc :424-428 "the syscall-shedding swap … cannot change what the tree shows"). 동작을 바꾸기로 하면 두 테스트의 기대값을 함께 뒤집어야 한다. 순환은 `expand` 가 사용자의 명시적 펼침에만 반응하고 재귀 프리로드가 없어 자동 순회 루프를 만들지 않지만, 안전을 위해 `ancestors_under_root`/`expand` 에 "이미 캐시된 canonical 경로" 가드를 함께 검토한다. **UX 동작 변경이므로 착수 전 사용자 확인(수정 vs 현행 유지) 권장.**

- **원인**: `close_tab`(:634-637)은 닫은 `Tab` 을 **필드 그대로** 스택에 넣고(`let closed = ClosedTab { tab, pane_id, index }; push_closed(layout, closed.clone());`), `Tab.dirty` 는 `#[serde(default)] pub dirty: bool`(`domain/layout/types.rs:108-109`)로 skip 없이 직렬화돼 `layout.json` 에도 남는다. 한편 같은 닫기 왕복에서 `releaseClosedFileTabPath` 가 `clearMirror` 로 미러를, `disposeModel(path)` 로 monaco 버퍼를 버린다. `reopen_closed`(:653)는 pop 한 `tab` 을 그대로 다시 삽입하며 dirty 를 초기화하지 않는다. 프런트에도 마운트 시 dirty 를 내리는 코드가 없다 — `use-editor-file-persistence.ts` 에서 `setTabDirty` 호출부는 전부 `{dirty:true}` 거나, 저장 정착 시 `{dirty:false}`(그것도 `if (dirtyRef.current)` 가드 아래인데 새 마운트의 `dirtyRef` 는 `useRef(false)` 로 시작해 이 분기에 못 들어간다)뿐이고, 미러 복원 경로는 미러가 있을 때만 도는데 미러는 ②에서 이미 지워졌다. 그리고 탭 바 dirty 점은 훅 로컬 state 가 아니라 백엔드 값을 직접 읽는다(`sortable-tab.tsx:108` `dirty={tab.dirty ?? false}`) — `editor-pane.tsx` 는 `tab.dirty` 를 전혀 읽지 않고 로컬 `useState(false)` 로만 관리하므로 두 값이 동기화될 경로가 애초에 없다. 이 불일치를 읽는 다른 소비자는 `handleCloseSaved`(`pane-tab-bar.tsx:154` `if (tab.pinned || tab.dirty) continue`)와 `retarget_file_tabs` 가 보고하는 `TabPathMove.dirty` 다.
- **수정안**: `push_closed` 가 스택에 넣기 전에 `closed.tab.dirty = false` 로 정규화한다 — 닫힌 시점의 버퍼가 프런트에서 이미 폐기되므로 스택의 dirty 는 어차피 되살릴 수 없는 죽은 정보다. 미러가 살아 있어 실제로 복원 가능한 경우는 재열기 시 `applyMirrorRestore` 가 `setDirty(true)` + `setTabDirty` 로 다시 세우므로 충돌하지 않는다. 회귀 테스트: dirty 탭을 `close_tab` 한 뒤 `layout.closed_tabs.last().tab.dirty == false`, `reopen_closed` 후에도 false.
- **주의점(fixNote)**: #8 의 후속 증상이지만 수정 지점이 달라 따로 다룬다 — #8 에 '저장 안 함' 버튼만 붙이고 dirty 를 내리지 않으면 이 증상은 그대로 남는다. 프런트 대안(마운트 시 미러가 없는데 `tab.dirty` 가 true 면 `setTabDirty(false)` 로 정정)은 라운드트립이 하나 더 필요해 부차적이다.

### 22. [tab-menu-6] `src/widgets/editor-area/pane-tab-bar.tsx:136` — 직렬 닫기 루프가 중간 실패 시 조용히 멈춘다

- **주의점(fixNote)**: `useCloseTab` 자체에 무조건 토스트를 붙이지 않는다 — 단일 닫기(X 버튼 등)에도 쓰이므로 호출부(루프) 쪽에서 처리하는 것이 맞다. 1차 조사 `tabbar-dnd` 는 이 코드를 보고도 "결정적 실패 조작을 특정 못 함" 으로 제외했고 `stale-ids` 는 "d-63 §7 과 같은 클래스" 로 재론하지 않았는데, d-63 §7 의 실제 변경 파일 5개에 `pane-tab-bar.tsx`·`editor-area.tsx` 는 없다 — 이 항목이 지적하는 것은 unhandled rejection 자체가 아니라 **사용자에게 보이는 부분자 완료 + 무통지**다.

### 23. [tree-watcher-search-1] `src/widgets/explorer/explorer-container.tsx:164` — 무시 디렉토리의 "폴더에서 찾기" 가 항상 0건이다

- **증상**: 사용자가 트리에서 명시적으로 지정한 검색 범위가 조용히 무시되고, "그 폴더에 그 문자열이 없다"는 **사실과 다른 결론**을 준다. 의존성 코드를 뒤지는 흔한 작업(라이브러리 구현 확인, 빌드 산출물 grep)이 통째로 실패하는데 실패했다는 신호가 없다.

  ```rust

  .filter_entry(|entry| {
      if entry.depth() == 0 { return true; }
      let is_dir = entry.file_type().map(|t| t.is_dir()).unwrap_or(false);

      !constants::is_ignored_dir(&entry.file_name().to_string_lossy())

  ```
  `passes_glob_filters`(:319)는 walk 가 **이미 내보낸** 엔트리에만 적용되므로 가지치기된 서브트리는 include glob 이 무엇이든 후보에 오르지 않는다. `search_run`(`commands.rs:82-88`)도 root 를 항상 프로젝트 루트로 고정해 target 폴더로 좁히지 않는다. `constants::IGNORED_DIR_NAMES` 는 `.git`·`node_modules`·`target`·`dist`·`build`·`.next`·`.turbo`·`.venv`·`venv`·`__pycache__`·`.cache`·`.idea` 등이다. 컨텍스트 메뉴 항목은 `isDirectory` 만 보고 무조건 노출된다(`features/explorer/file-tree-context-menu.tsx:159-165`). **d-64 이전에는 이 행 자체가 트리에 없어 도달 불가였다**(`domain/tree/service.rs:49-54` JSDoc: "Nothing is filtered out (d-64 T1, user decision 2026-09-16)"). `docs/features/explorer-sidebar.md` §2.3 은 "트리가 보여주는 파일 집합과 검색이 찾는 집합이 일치하지 않는다" 까지만 적었고 **이 메뉴 항목이 조용한 무동작이 되는 것은 기록되어 있지 않다.**
- **수정안**: 둘 중 하나로 정한다(**제품 판단 필요 — 사용자 확인 권장**). ① **범위 우선**: `configure_walk` 의 `filter_entry` 가 `query.include_glob` 의 첫 경로 성분과 일치하는 서브트리는 가지치기에서 면제하도록 walk 설정에 include 힌트를 전달한다(단 "폴더 스코프" 와 "자유 glob" 을 구분해야 일반 검색의 수동 include 패턴에 영향이 없다). ② **정직한 거부**: `file-tree-context-menu.tsx` 에서 행 경로에 무시 성분이 있으면 항목을 비활성화하고 사유 툴팁("검색 색인에서 제외된 폴더")을 단다 — 최소 변경이며 거짓 0건을 없앤다. 단 프런트에 `IGNORED_DIR_NAMES` 가 없으므로(Rust `constants.rs` 에만 존재) bindings 로 노출하는 작업이 선행돼야 한다.

### 24. [tree-watcher-search-3] `src/widgets/explorer/explorer-container.tsx:231` — "모두 접기" 가 화면 밖 펼침 상태를 남긴다
